# 06. Prefill — 計算律速に切り替わる世界

> 対象: `src/prefill/gemm.cu`（873）、`wmma_gemm.cu`（737）、`moe_fused.cu`（728）、
> `moe_fused_iq.cu`（1215）、`moe_mmq.cu`（298）、`kernels.cu`（2214）、
> `gdn_rec_parity.cu`（1383）、`gemm_bf16_parity.cu`（155）、`ggml_cuda_host.cu`（147）
>
> 図: [06 prefill — チャンク → 密 GEMM → expert GEMM 4 系統](../diagrams/prefill.svg)

decode は**帯域律速**（[03](03_decode_gemv.md)）だった。prefill は**計算律速**になる。
だからカーネルも、データ配置も、使う命令も、全部違う。Strata は decode 用と prefill 用に
**別々の実装を持つ**（融合しない）という選択をしている。

---

## 1. prefill の流れ

```
プロンプト（最大 8,192 トークンのチャンク。32,768 は --opt-in）
   │
   ├─ attention / GDN / GR はバッチ GEMM（ライブラリ or WMMA）
   ├─ router で各トークンの top-10 を決め、expert ごとにグループ化
   ├─ 必要 expert を RAM/SSD → VRAM へ PCIe でストリーム
   │     └ リングは 0.1.39b 以降【バイト単位】でサイズ指定（#583）
   └─ expert の GEMM を int8 テンソルコアで
```

関連する環境変数（`docs/` と `HOW_IT_WORKS.md` から）:

| 変数 | 意味 |
|---|---|
| `STRATA_RING_BYTES` | expert リングのバイトサイズ（#583 以降） |
| `STRATA_PREFILL_CPU_SHARE` | どれだけの expert を CPU 側で計算するか |
| `STRATA_ROUTE_TAIL_SKIP` | ルーティング末尾のスキップ |
| `--pcie-frac` | PCIe 帯域の配分（ブランチ f-142） |
| `--aux-cpus` | CPU プールに使うコア数 |
| `STRATA_PREFILL_BF16X2` | BF16 2 項分割（後述） |

## 2. GEMM は 4 系統ある

| 系統 | ファイル | 使う場面 |
|---|---|---|
| cuBLAS / hipBLASLt | `gemm.cu` | 大型の BF16/FP16 GEMM。ベンダー最適化に任せる |
| RDNA3 WMMA | `wmma_gemm.cu` | gfx1100/1101/1102/1150/1151 で自前タイル |
| 自前 int8 テンソルコア MoE | `moe_fused.cu`, `moe_fused_iq.cu` | Q2_0 / i-quant の expert を直接 |
| ggml MMQ | `moe_mmq.cu` | llama.cpp の MMQ をピン留め checkout からコンパイル |

### 2.1 「BF16 テンソルコアが無いカード」の長い歴史

これはコードコメントが最も饒舌な部分のひとつ。

> 「Turing と Volta には BF16 テンソルコアが無い: `cublasGemmEx` は `CUDA_R_16BF` 入力で
> **SIMT fp32 カーネル（magma_sgemmEx）に落ちる**。RTX 2080 Ti で 4K プロンプトの 1/5（#655）、
> V100 でプロンプトの約 10%（#540）。」

解決は「**BF16 → FP16 は FP16 の正規範囲内で厳密**」（7 ビット仮数は 10 ビットに収まる）:

> 「重みと正規化済み活性はその範囲にある。FP16 経路では、重みは呼び出しごとに 1 回、
> 活性は行スライス単位で変換され、インスタンス自身のバッファに入り、積は
> テンソルコア上の FP16 GEMM（fp32 アキュムレート）として走る。
> **FP16 の範囲を超える有限値は Inf ではなく ±65504 にクランプする**（#540）。
> beta = 1 の積（`STRATA_PREFILL_BF16X2` の残り、元の約 2⁻⁹、FP16 の非正規数帯の深部）だけは
> cuBLAS に残す。」

既定値まで書いてある: compute capability 7.0–7.4 で ON、7.5（RTX 20）は**和の丸めが変わる**ので
ゲートされるまで opt-in。Pascal（6.x）はテンソルコアが無く cuBLAS に BF16 GEMM も無い
（#395、P40 で NOT_SUPPORTED 実測）ので、**両オペランドを正確なシフトで fp32 に広げて `cublasSgemm`**。

> **このエンジンの一般則**: 特定世代のハードで「ライブラリが静かに遅い経路に落ちる」場合、
> **意味を保ったまま別の型に写して速い経路に乗せる**。そのために「その写像が厳密である条件」を
> コメントに書く（ここでは「FP16 の正規範囲内」）。

## 3. MoE の int8 テンソルコア — magic float の完全な説明

`moe_fused.cu` 冒頭は、このエンジンで一番美しいトリックを解説している。

### 3.1 代数

Q2_0 の 1 ブロックは 64 重み `w = d_w * (q - 1)`、`q ∈ 0..3`、1 バイトに 4 コード。
活性の 32 値ブロックは `x = d_x * a`、`a = round(x / d_x) ∈ -127..127`。32 値の半ブロックで:

```
sum w x = d_w * d_x * ( sum q a - sum a )
```

> 「int8 の積はコードを**そのまま**取る（0..3 は有効な s8）。オフセットは活性自身の和で、
> ブロックと一緒に保存される。」

### 3.2 整数 → float を 1 命令で

> 「ドット積（|sum q a| ≤ 32·3·127 < 2²²）は **1 回の整数加算で厳密に float になる**:
> `as_float(0x4B400000 + dot) = 1.5 * 2²³ + dot`。そしてブロックは
> `c = -(1.5 * 2²³ + sum a)` を保存する。だから
> `as_float(0x4B400000 + dot) + c = dot - sum a` が**丸め無しで**得られる。」

なぜこれが成り立つか: IEEE754 の単精度で指数部が 2²³ 桁の値 `1.5 × 2²³ = 12,582,912` は、
仮数部が 23 ビットなので **整数を 1 ずつ正確に表現できる**。そこに `dot` を足すと、
下位 23 ビットがそのまま整数として入る。つまり「整数 → float 変換命令」を省いている。

出力・64 ブロックあたり:

```
acc += d_w * (d_x0 * t0 + d_x1 * t1)      # t = 各半ブロックの dot - sum a
```

> 「整数加算 2、float 加算 2、積和 3。」

### 3.3 K の並び — mma の都合に合わせて「意味を張り替える」

> 「`mma.sync m16n8k32` は行（A）または列（B）の**連続する 4 つの k** を 1 レジスタに取る。
> 連続する 4 重みは 1 コードバイト。**だが 1 レジスタの 4 コードは代わりに、
> 連続する 4 バイトの同じ 2 ビットフィールドから来る** —
> `(word >> 2t) & 0x03030303` は 16 重みワードの重み `t, t+4, t+8, t+12` を保持する。
> だからカーネルはこの順序を半ブロックの k に使う:
> **mma の k 添字 `16h + 4t + j` は、重み（と活性）`16h + t + 4j` を意味する。**」

活性はその順に保存され（`perm32`）、レーンの 2 つの B レジスタ（h = 0 と 1）が隣接するので
**1 回の 8 バイトロード**で済む。 → [04](04_moe.md) の「組み替えるのは活性のほう」と同じ発想。

### 3.4 blob の形

```
gate/up codes [1280][640 B]   （行が交互: 特徴 f の gate が行 2f、その up が行 2f+1）
down    codes [2560][160 B]
gate/up scales [1280][40] fp16
down    scales [2560][10] fp16
```

**gate と up を交互に置く**のが [04](04_moe.md) の gate-major 修正の prefill 版。
1 つの work item = 「expert e の最大 64 ルーティング行のタイル」×「256 重み行のブロック」で、
**永続グリッド**がバッチの item を歩く（個数はデバイス上にある）。


### 3.5 i-quant 版 — コードブックを int8 に「復号してから」積む

`moe_fused_iq.cu`（1215 行）は IQ 系を同じ枠組みに載せる。手順は:

1. コードブックから**重みを int8 に復号**する（i-quant の各形式は「符号 + グリッド」なので復号可能）
2. 以降は Q2_0 と同じく int8 テンソルコア

対応ブロックサイズ（[02](02_quant.md) の再掲）:
`iq2_xxs 66`, `iq2_xs 74`, `iq2_s 82`, `iq3_xxs 98`, `iq3_s 110`, `iq4_xs 136`, `q2_0 18`。

つまり **prefill は形式を吸収する層**であり、decode の「3 つのコード幅」ほど単純ではないが、
「復号 → int8 → テンソルコア」という 1 本の道に集約されている。

### 3.6 ggml MMQ をそのまま使う経路

`moe_mmq.cu` は llama.cpp の MMQ（`ggml-cuda`、MIT）を**ピン留めした checkout からコンパイル**し、
`ggml_cuda_host.cu`（147 行）が `ggml-cuda.cu` が参照する少数のホストシンボルを供給する。

> 「Strata blob の Q2_0 ブロックは `{f16 d; 16 code bytes}` で、同じ順序の同じ 2 ビットコードを持つ。
> つまり**ブロックは 1 スケールと 16 バイトのコード列**である。」

「自前実装を書く前に、参照実装がそのまま使えるなら使う」という判断。
ただし`moe_fused.cu` の方が速い（自前のグループ化と融合があるため）ので、
MMQ は**比較対象とフォールバック**の位置づけになっている。

## 4. RDNA3 の WMMA — ビルド定義でなければ動かない話

`wmma_gemm.cu` のヘッダは `v_wmma_f32_16x16x16_f16_w32` などの intrinsic を使う。
問題は「このコードが有効かどうかをどう判定するか」。

> 「`STRATA_WMMA_GFX11` は**ビルドが定義する**（CMakeLists.txt、`CMAKE_HIP_ARCHITECTURES` から）。
> コンパイラマクロから推論してはいけない:
> **このツールチェーンで実測したところ、HIP コンパイルのホストパスは `__gfx1100__` を定義しないが
> `__HIP_DEVICE_COMPILE__` は定義する。** だからここでコンパイラマクロのガードを書くと、
> エンジンがリンクするまさにそのシンボルに対して、ファイル末尾の “return false” スタブが
> **静かに選ばれる** — WMMA 経路は決して走らず、同じファイルを hipcc で（プローブがそうするように）
> コンパイルすると実ブランチを取る。**ビルド定義のマクロ 1 つなら、ホストパスとデバイスパスで一様。**」

これは「静かに機能しなくなる」系の最悪例: ビルドは成功し、テストも（WMMA を使わないテストなら）通り、
性能だけが落ちる。

タイル変種は 2 つ:

| 変種 | スレッド | タイル | 特徴 |
|---|---|---|---|
| `gemm_wmma_16x16_1w` | 32（1 wave） | 16T × 16N × 16K | LDS 0、バリア 0、全レジスタ常駐。小さい T/N 用 |
| `gemm_wmma_64x64_4w` | 128（4 wave） | 64T × 64N × 16K | W 用 LDS 4 KB のダブルバッファ、128 ビット協調ロード |

ウェーブ 32 のフラグメント配置も明記されている（レーン t は A の行 `t & 15` と B の列 `t & 15` を持ち、
レーン 16..31 は 0..15 の複製、C は列 `t & 15` の 16×16 タイルを 8 要素交互の行で持つ）。

## 5. `gemm.cu` — 地味だが危険な 3 つの話

### 5.1 in-place の FP16 → FP32 拡張

> 「Y の行は FP16 出力 GEMM によって各 FP32 行の先頭に FP16 として書かれ（`ldc = 2 ldy` ハーフ）、
> その場で拡張される。float の c はハーフ 2c と 2c+1 を上書きするので、**行はその終端から
> ブロック単位で歩く**: ブロックのハーフをレジスタに読み、ブロックが同期し、それから float を書く —
> 書くのは既に読んだブロックのハーフだけを覆う。」

「同じバッファの上で型を変える」処理は、**後ろから書く**のが定石。

### 5.2 `STRATA_DBG_NAN`

> 「STRATA_DBG_NAN: 有限でない FP16 出力（fp32 で蓄積した和が 65504 を超えると FP16 で inf になる）。」

FP16 出力の GEMM は**静かに inf を作る**。だから専用のデバッグフラグがある。

### 5.3 Windows の hipBLAS が返す「成功したのにエラー」

> 「#247/#325: Windows（gfx1201 で観測）で、hipBLAS は一部の形状（T ≥ 96 で hc が 1 回、
> router）で正しい BF16/FP16 積を返しながら、`hipErrorInvalidValue` をセットしたままにできる。
> 次のカーネルのエラー検査がそれを exit に変える。**積は完了しているので、成功した GEMM の後で
> その古いエラーを 1 つだけクリアする**。他のエラーは今まで通りエンジンを止める。
> Windows のみ: Linux では古い `hipErrorInvalidValue` は前の呼び出しからの本物のエラーであり、
> 報告され続ける。」

**「ライブラリのバグを、プラットフォームを限定して、理由を書いて回避する」** —
回避 code に理由と範囲が書かれていないと、後で全プラットフォームに広がって本当のバグを隠す。

## 6. `kernels.cu` — prefill の「融合」カタログ

2,214 行。prefill の注意機構・GDN・PLE・postops がここにあり、**「同じビットのまま 2 つを 1 つにする」**
融合が並ぶ。読むときに覚えておくべき原則は decode と同じ:

> **bits が同じであることを証明できる融合だけが既定で ON になる。**

### 6.1 ハイパーコネクション（GR）系

| 融合 | 内容 |
|---|---|
| F-1 | 行スケールと BF16 イメージだけ書く。`gr_mix_r_kernel` が **r × rs × w を自分で同じ順で再計算**するので、正規化行の FP32 コピー（T × 10240 float）を書かず読まない |
| F-2 | `gr_write_kernel`（1 行 1 スレッド (t,c)）と `gr_norm_rs_kernel` の縮約を融合。**同じスレッド→要素の対応**（256 スレッド、ストライド 256）と同じ `block_sum` なので rs と BF16 イメージが同じビット、R を読み戻さない |
| S23 `STRATA_CVEC_FUSE=1` | steered 層の FFN 書き込み + 制御ベクトル + 次のハーフの norm を **R 上の 1 パス**で（元は gr_write + cvec_apply + gr_norm_rs の 3 つ）。書き込みは gr_write_kernel の、ベクトルは cvec_kernel の（d = tid + 256k 上の同じスレッド毎ドット順、同じ 2 段 xor 縮約）、norm は gr_norm_rs_kernel の（同じ ss 順と block_sum）→ 同じビット |

### 6.2 GDN 系

| 融合 | 内容 |
|---|---|
| C-3 | 同じ 4 タップ因果 conv を**トークンでタイル化**: スレッド (c, tile) が自分のタイルの 3 つの先行入力をチャンク（またはその前の履歴）から読む。conv は入力を読むのであって自分の出力を読まない → タイルは独立、要素ごとに同じ式（同じビット）、履歴は後で書く |
| Aurora S23 `STRATA_GDN_CONVL2=1` | `gdn_conv_tiled_kernel` に `gdn_l2_kernel` を折り込む。**ブロックの 128 スレッド = 1 ヘッドの 128 チャネル**なので、q / k ヘッド（block < 2·HK）では norm の二乗和がブロックのそれになる: 同じ `warp_sum`、同じ 4 つの部分和を同じ順で加算、同じ格納値に対する同じ `v * rsqrtf(ss + eps)` → 同じビット、しかも h を書いて読み戻さない（16 トークン/ラウンド） |
| D-2 | 再帰の**値列を 1 ヘッドあたり 4 ブロックに分割**（上のカーネルの 4 倍のブロック数） |
| `gdn_history_advance` | チャンク後の履歴（最後の 3 入力。チャンクが 3 より短ければより古い履歴） |

### 6.3 PLE（28.8 GB の n-gram テーブル）

PLE は **SSD 上 28.8 GB の n-gram テーブル**で、トークンごとに数行だけを**非バッファ（unbuffered）読み**する。
`--ple-io direct` が既定（[01](01_memory.md)）。prefill でもチャンク全体でその行集合を引くが、
**テーブル本体は GPU に載らない**（載せたら VRAM が終わる）。GPU 側の演算は
`ple.cu` / `native_ple_postops.cu`（[07](07_misc.md) で詳述）が担う。

## 7. 数値契約を守るための専用ハーネス

prefill には **parity（一致）専用の実行ファイル**が 2 本ある。製品コードではなく、**契約の証明**。

| ファイル | 行 | 何を突き合わせるか |
|---|---|---|
| `gdn_rec_parity.cu` | 1,383 | GDN 再帰の **chunked prefill 経路 vs 逐次 decode 経路**。トークン毎の演算を同じ順序で書き写してあるので、prefill のチャンク計算が plain decode とビット一致することを検証できる |
| `gemm_bf16_parity.cu` | 155 | BF16 GEMM の各経路（cuBLAS / FP16 経由 / SIMT フォールバック）の一致 |

これがあるから「prefill は速い経路、decode は別経路」という**二重実装**が成立している。
ハーネスが無ければ、二重実装は必ずどこかで食い違う。

## 8. この章のまとめ — decode と prefill の対比

| 観点 | decode（[03](03_decode_gemv.md)–[05](05_attention_gdn.md)） | prefill（本章） |
|---|---|---|
| 律速 | **帯域**（38 GiB パックを毎トークン読む） | **計算**（8,192 トークンを一気に） |
| GEMM | 自前 GEMV（`s_gemv` 系）、1 トークン | ベンダー GEMM / WMMA / 自前 int8 MoE |
| 量子化 | その場で復号しながら積む（Q8_0 / Q8_K 活性） | BF16 / FP16 に写す、または int8 テンソルコア（magic float） |
| expert | 必要なら CPU プールで並行計算 | PCIe でストリーム（リングはバイト単位） |
| 融合 | doorbell で GPU/CPU を重ねる | 同一ビットの証明できる融合だけ |
| 検証 | `*_parity` カーネル | `gdn_rec_parity` / `gemm_bf16_parity` |

### 読者チェックリスト

1. なぜ prefill だけ別実装なのか（律速が違う → 最適解が違う）を説明できるか
2. `as_float(0x4B400000 + dot)` が**なぜ丸め無しで整数→float になる**か導けるか
3. mma の k 添字 `16h + 4t + j` が重み `16h + t + 4j` を意味する理由を言えるか
4. BF16 → FP16 の写像が**どこで厳密で、どこでクランプが要る**か
5. `STRATA_WMMA_GFX11` をコンパイラマクロから取ってはいけない理由
6. in-place の FP16 → FP32 拡張が**なぜ行の終端から**書くのか
7. 「Windows だけ古いエラーを消す」がなぜ安全と言えるのか
8. parity ハーネスが無いと二重実装はなぜ破綻するか
